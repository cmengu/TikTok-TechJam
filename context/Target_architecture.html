The External Oracle

The last read told you what was broken without telling you what you were building toward. This one starts at the destination — a named rung on a published autonomy ladder, one component away — and derives the path back to tonight.

The destination, stated once

A search loop in which no result is believed on the strength of the same distribution that produced it.

The August 2026 survey of autonomous research agents grades systems L0 to L5 and splits the closed-loop tier in two. L4-m is mechanical: the loop re-runs on its own internal metric. L4-v is validated: revisions are gated by an external oracle the search cannot game. Of twenty-four systems it audits, nine reach L4. Seven are mechanical, one is author-claimed, and exactly one is externally validated — CAMEO, from 2020, which is not an LLM system at all.

No LLM-era system in that corpus demonstrates an in-loop external oracle. KuaiRand hands you one for free: log_random_4_22_to_5_08_pure.csv, roughly 1.18 million randomly exposed impressions, unpolluted by the logging policy that generated every other split. Wiring it in as a promotion gate is about an hour of work and it moves the harness from the tier everyone is in to the tier one pre-LLM system occupies.

One boundary, from the rules: the scored submission is fixed as the validation-best checkpoint at convergence, so the oracle gates what the search keeps, not what it finally submits. And the test split — public data, physically on your disk — is out of scope during development and must never be read by a run.

That is where you are going. Everything below either builds toward it or is deliberately cut.

Two things make L4-v reachable rather than aspirational for you. The random-exposure log is a genuine external oracle — it was collected under a different policy, so a model that scores well by agreeing with the production recommender gets no credit from it. NOVA

Tencent's harness, in full

A Verification-Aware Agent Harness for Architecture Evolution in Industrial Recommender Systems, arXiv:2606.27243, 20 authors. Read this one closely: it is the same object as your tree, built by people with a billion users and a production A/B test at the end of it.

The state and the objective

Architecture state A_t = (G_t, φ_t, F_t)
G = model graph · φ = structural hyper-parameters · F = feature configuration

Two-stage objective offline: max_A J_offline(A) = AUC(A), A ∈ A_Ω
online: J_online(A) = Σ_i w_i · m_i(A), m_i ∈ {GMV, Bias}
The decomposition of the state into graph, hyper-parameters and features is worth adopting verbatim, because it is also a taxonomy of modification kinds — and your Stage literal (data / features / objective / architecture / training / ensemble) is already a finer-grained version of the same idea. Ω is the hard-constraint set: interface compatibility, tensor shapes, dtypes, feature availability, framework and serving compatibility, latency, parameter and FLOPs budgets. Yours is smaller and mostly about leakage, which is the right translation.

The architecture gradient

Equation 5 g_t = Grad(e_{t−1}, V_t, ΔJ_t, H_t)

g_t.weak_components → which part of (G, φ, F) is the bottleneck
g_t.directions → which families to explore next
g_t.forbidden → patterns that failed, were invalid, or went negative
Not a number — a structured object with three named fields, recomputed every round from the last edit, its verification diagnostics, its measured delta, and the whole history. Your family_stats() → Queue.score_hyp() path implements the middle field and nothing else.

Forbidden entries are stored in a specific shape: an edit-pattern mapped to a defect-class, tagged with the round that produced it. The paper's own example is a rule learned in round 7 — sequence self-attention without a causal mask → future-information leakage. That is exactly the schema candidate/rules.jsonl already has, down to the statement / pattern / severity split.

AgentX

Kuaishou's engine, in full

Towards Agent-Driven Self-Iteration of Industrial Recommender Systems, arXiv:2606.26859, 62 authors, deployed. Four stages over a shared knowledge layer, plus a layer that rewrites the agents themselves.

The knowledge layer — four bases, not one

  • Experiment KB — historical launch reviews: target scenario, affected user groups, metric movements, launch decision, post-hoc diagnosis. Queried when a proposal needs empirical precedent.
  • System KB — a three-layer domain wiki: a schema layer defining field types and relations, a wiki layer of standardised Markdown entries, and a raw-source layer linking each entry back to the code it describes. Built by extractor agents, not by hand.
  • Data Analysis — metric definitions, SQL plans, offline statistics; validates that a proposed segment is actually big enough to move a metric.
  • Model Research — papers decomposed into typed claims: problem, assumption, method, finding, limitation, plus architecture components and inter-paper relations, each grounded against production feature contracts.

The three-layer System KB is the transferable idea. An entry is only trusted because it links back to the source it was extracted from — which is the same discipline as your rule that no state exists that is not a fold over the event log.

How a proposal is scored

Brainstorm ranking S(c|q) = λ_o·O(c,q) + λ_b·B(c) + λ_f·F(c) + λ_h·H(c) + λ_e·E(c|q) − λ_r·R(c)
E(c|q) = Σ_k α_k(q,c) · e_k(c) over the four knowledge bases
Objective alignment, business validity, feasibility, handoff completeness, evidence, minus risk. Handoff completeness is the surprising term: a proposal is scored partly on whether it is specified well enough for the next agent to act on without asking. Ideas are also bucketed as ready-to-implement, probe-first, or moonshot-backlog rather than ranked on one axis — which is a better fit for your convergence rule than a single expected_gain float.

The model-developing state machine

Section 5.2 policy → (code ↔ verify)_{≤3 rewrites} | experts×N_{concurrent} → exec → final_review
Every stage has a deterministic exit condition. The rewrite budget is three and exhausting it fails the round cleanly rather than escalating. The expert panel votes in Python and needs a ⌈2N/3⌉ supermajority. Execution is a pure Python finite state machine with no model in it at all — submission, polling, metric extraction by regex from the training log.

Before any code is written, the agent declares a policy: what changes, the causal mechanism claimed, and a set of expected observables with names and thresholds — the paper's example reads “gate activation > 0.5 after step 1000 indicates a live gate; ≈ 0 indicates collapse.” The verify step then checks two things: that the diff semantically matches the declared direction, and that every declared observable actually appears in the code.

The example that justifies the whole mechanism

Round 1 — rejected at +0.0003 AUC

A multiplicative gate, x·tanh(V_o x). The code was correct and the metric improved. But the declared observable showed gate activation near zero for the entire run: Glorot initialisation made V_o x ≈ 0, which zeroed the tanh output and blocked gradients. The gate never fired, so the gain could not be attributed to the gate. Attribution UNCLEAR — the improvement was discarded.

Round 2 — accepted at +0.0022 AUC

The residual fix, x·(1 + tanh(V_o x)). Activation recovered, every link in the causal chain verified. Attribution CLEAR — recorded.

Under your ε = 0.002 / N = 3 convergence rule, a +0.0003 result does not reset the counter — but a noise-driven +0.0025 would, and would then pull the search into a family that does nothing. That is the failure this brake exists to stop, and your measure.py already implements the consumer side of it.

The eight-dimension code score

Q_code Q = .06·s₁ + .12·s₂ + .22·s₃ + .08·s₄ + .06·s₅ + .18·s₆ + .18·s₇ + .10·s₈
The three heavy terms — 58% of the weight — are attribute hallucination, correctness-loop iterations, and manual operator interventions. Kuaishou scores its own agent on how often a human had to step in, and so does the TechJam rubric under Impact & Relevance. Your intervention event exists for exactly this; make sure the final report quotes the count.

SGPO — correctly declined, worth understanding

Two variants. SGPO-I samples dialogue traces, produces a natural-language loss report plus a structured semantic gradient (missing constraints, weak step ordering, underspecified evidence), refines one subagent's prompt, then admits the edit only if a paired replay on identical tasks improves the score by more than ε. Five rounds took the brainstorm agent from 75.2% to 98.0%, and the accepted edits are legible: make the task contract explicit before generating, require an explicit evidence index, standardise the candidate schema, separate novelty from duplicates. SGPO-II does the same for the coding agent using historical merged requests instead of traces, filtered to drop bulk reformats, reverts, diffs under 10 lines and over 5000, then replayed as requirement-only tasks against the landed patch.

It needs a trace corpus and a replay harness. You have neither and two days. Keep declining it — but note that GEPA below is the same idea at a hundredth of the cost, and is the right thing to reach for after the deadline.

Field

Nine adjacent systems, and what each contributes

Sorted by what they add to the blueprint above, not by fame. The first three change what you should build; the rest are the reading queue for after 1 September.

AIRA-2 · arXiv:2603.26499 Changes the design

The single most relevant paper on this page, and it overturns a result the field had accepted. Earlier work found that picking the final submission by true test score instead of validation score would raise MLE-bench medal rates by 9–13% absolute, and everyone read that as the agent overfitting the validation split during search.

AIRA-2's ablations show it was mostly evaluation noise, not memorisation — self-reported metrics, dynamic splits, and outright evaluation bugs producing perfect validation scores regardless of input. Their fix, Hidden Consistent Evaluation, is three rules: one fixed split made once and reused identically across every seed; labels hidden from the agent; scoring externalised into a separate container. Then the signals are decoupled — one split steers the search, a different one selects the final submission. Removing HCE costs about 13 percentile points, the largest ablation in the paper.

What it means for you: you already have the good version of two of these — evaluate.py is frozen and externally supplied, and the splits are fixed date ranges rather than resampled. The third is the one you are missing, and it is the destination: search on validation, select on something else. Their second finding is a scaling law where the compute-optimal number of parallel agents grows as the square root of the budget — breadth beats sequential depth. On a 40-second training run that argues for running all three candidates rather than ranking them.

MLE-STAR · arXiv:2506.15692, NeurIPS 2025 Changes the design

The mechanism your loop is missing on the generation side. Instead of asking the model what to try next, MLE-STAR runs an ablation over the candidate's own code blocks to find which pipeline component most affects the score, then concentrates the search inside that component. It is a nested loop: outer picks the target block, inner explores variants of it.

This is NOVA's weak_components field — the one you have no implementation of — computed cheaply and mechanically instead of being asked of a model. On a 40-second training run, ablating the four blocks of the reference pipeline costs under three minutes and tells you where the signal is. It also directly attacks your worst failure mode: three duds in a row ends the run, and an ablation-directed proposal is far less likely to be a dud than a bank-ordered one.

Autonomous Research Agents: a survey of AI scientists and the verification gap · arXiv:2608.05179 Frames the claim

Where the L0–L5 ladder comes from, and the source of the destination on this page. Its headline audit: across 24 runnable systems, 83% release code but only 38% release seeds or execution traces, and only 38% report any novelty-verification method. Its stated conclusion is that code availability is no longer the scarce thing — evidence that a claim can be checked is.

Your harness is unusually well positioned against that specific critique: the run is the trace, replayable, with seeds recorded per rung. Say so explicitly in the write-up and cite this survey for why it matters. Its failure-mode list also reads as a checklist of things to avoid claiming — novelty-proxy gap, compile-versus-reproduce gap, LLM-as-judge unreliability, and the absence of negative results in reported runs.

The auto-fine-tuning branch — after the deadline

You asked specifically about auto fine-tuning loops. That is a live and separate literature, and it is the natural continuation of this harness once the task stops being a factorization machine. I found these by title and abstract only and have not read them properly — treat this as a reading queue rather than a set of claims.

  • PostTrainBench arXiv:2603.08640 — can LLM agents automate post-training? The benchmark for exactly this question; the headline is partial success with premature convergence as a named failure mode, which is your convergence rule in another costume.
  • TREX arXiv:2604.14116 — automating LLM fine-tuning via agent-driven tree-based exploration; a Researcher module plus an Executor wired to a GPU cluster. The closest structural match to your harness in the fine-tuning setting.
  • LLMZero arXiv:2606.18388 — discovering adaptive training strategies for RL post-training via LLM agents.
  • Pioneer Agent arXiv:2604.09791 — continual improvement of small models in production, using Monte-Carlo graph search where nodes are whole training pipelines.
  • AutoLLMResearch arXiv:2605.11518 — learning from cheap experiments to optimise expensive ones, which is the ladder idea generalised.
  • Agentic Neural Architecture Search arXiv:2607.07984 — the NAS-flavoured cousin of NOVA.

Three of these — TREX, Pioneer Agent, AutoLLMResearch — are tree or graph search over training pipelines with a cheap-to-expensive rung structure. That is your harness with a different candidate type. If this project continues past September, the honest framing is not “a hackathon entry” but a task-agnostic search harness whose first task happened to be a recommender.
