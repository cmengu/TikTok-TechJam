Every file, by folder — and three answers

The runbook's first diagram draws the twenty files that touch one KuaiRand rung. The repository has 95 tracked or generated files plus the eight in the starter kit, and the runbook's diagram leaves out the whole LLM side (harness/agents/), the live view (app/), the nineteen test files, the hypothesis bank and its patches, the tuner, the fake-run stream, three dead Ali-CCP tracks and three dead phase-6 scripts. This page draws all of it, split by folder, with what is on disk lit and what the fourteen steps still owe ghosted. Read the three answers first — they are what you asked.

three answers — oracle · template · runner

1The oracle is inside the task's terms — under the organisers' own name, not ours

"Oracle" is our word; the organisers never use it for this. But their kit README lists seven untried directions, and direction 7 is the random-exposure log itself: log_random_4_22_to_5_08_pure.csv "can serve as an additional unbiased validation set, to check whether the model only overfits biased traffic." That is precisely the job the runbook gives it — a second validation signal that gates promotions inside the loop while the scored submission stays the validation-best checkpoint the rules demand.

evidenceKit README §从哪里开始改, item 7. The one hard rule is no external training data — the random log is inside KuaiRand-Pure and is never trained on, only predicted on. Hidden-test rule — its labels sit under harness_only/ and only the scorer reads them.

catchTwo. (a) The kit uses "oracle" for something else: the perfect-ranking ceiling, primary 0.8645 on test ("评估进展请以 oracle 为分母"). In the write-up call ours the random-exposure gate or unbiased validation, or a judge reads "oracle" as "they used the labels". (b) The random log spans 22 Apr – 8 May and the hidden test is 29 Apr – 8 May. Runbook step 2 writes the whole file "file order kept", yet its own verify line says no candidate-visible file may hold test-dated rows — the two contradict. Pick one: filter the oracle to 22–28 Apr (matches valid, loses roughly 40% of rows, keeps the claim "no test-era information touched development" clean) or keep it whole and delete the verify line. My pick is filter.

todayNothing on disk can hand the candidate an oracle: runner._build_env ends with assert set(candidate_env) <= {"TRAIN","VALID"} (runner.py:550). Step 4 widens that wall; until then the oracle is a plan, not a path.

2template.py is hard-coded to the synthetic spec, not KuaiRand — and that spec is copied by hand in three places

What is on disk is the synthetic-task candidate: a torch MLP, parquet in and out, rows keyed by sample_id, five fixed columns (user_id item_id cat_a cat_b cat_c), two heads p_click and p_conversion_given_click, and a SYNTHETIC_FAIL switch so the failure tests can make it crash, hang, or OOM on cue. The runbook table's row — "reads $TRAIN $VALID [$ORACLE] $SEED, numpy + csv, writes preds.csv" — describes the file after step 6, not today.

evidencetemplate.py:20 BASE_FEATURES; :215 writes sample_id, p_click, p_conversion_given_click; protocols/synthetic.yaml metrics.cvr_auc.output: p_conversion_given_click; rules.jsonl C3 requires that literal by regex.

so is it "defined by the spec"?Only by hand. The yaml declares the output name, C3 demands it, the template writes it — three copies, nothing derives one from another, and only the tests notice drift. KuaiRand means rewriting all three in lockstep: yaml in step 3.1, template in step 6, rules in step 13. What is not hard-coded is the knobs: FEATURES BATCH LR EPOCHS DEVICE SEED arrive as environment variables that runner._build_env assembles from run_cfg, and the tuner overrides them per trial.

insightA hand hypothesis is one knob frozen into the file: f_true.diff replaces os.environ.get("FEATURES") with the literal "base,f_true". The bank hypotheses have no diff at all — the LLM coder writes one at run time.

3The runner does not "do" the hypothesis — a hypothesis is a diff, and the runner only launches what the diff produced

The path, file by file: hand.yaml or bank.yaml → a Hypothesis (types.py) → Queue (tree.py:147, ordered by p_win and family stats) → Tree.step pops one → coder.materialise: PatchCoder (tree.py:72) just returns the yaml's patch path, LLMCoder (agents/coder.py) asks the model for a diff and checks it against contract.py → Workspace.commit_node (tree.py:117) git-applies the diff inside runs/<id>/workspace and copies it to patches/node-NNN.diff → only now the runner: _stage_candidate (runner.py:475) copies template.py + report.py out of that git tree into workspace/node-N/attempt-M/, _build_env (:496) builds the wall, LocalBackend.run Popens it (:188) and watches progress.jsonl → task.score(preds) → measure verdict → events.jsonl.

what the runner does ownStaging, the capability wall, the process, the stall watchdog and hard timeout, and failure classification (crash / oom_cuda / oom_host / hang / nan / bad_schema) with a halved-batch retry. That is real logic — it is just never "what to try next".

catchThe same Hypothesis object arrives by two routes that meet in the same workspace: --hypotheses hand.yaml (patch on disk, no LLM) or the default (bank.yaml + propose, LLM writes the patch). The dashed rose line on the map is the one process boundary in the system; everything left of it is harness, everything the candidate can read crosses it as an environment variable.

insightAsk "who edits the file?" (tree + coder) separately from "who runs the file?" (runner). The runbook's fourteen steps touch the first for KuaiRand only in step 6 and 13; steps 3–5 are all on the runner/measure side.

one rung, start to finish — as it runs today on the synthetic task

  1. python -m harness run --hypotheses hypotheses/hand.yaml — __main__.py loads protocols/synthetic.yaml through protocol.load, hashes the ruler, constructs SyntheticTask (hardcoded), opens EventLog which writes the run header into runs/<id>/events.jsonl.
  2. synthetic.prepare() generates the data, writes runs/<id>/data/{train, search_validation, holdout_validation}.parquet, verifies the five digests in the yaml. A placeholder digest (hex ≤ 15) skips verification — that is a bypass, and a test forbids it in real runs.
  3. Tree.calibrate_baseline runs the untouched template on five seeds to set σ; then Queue.pop yields h-f-true, and PatchCoder.materialise returns hypotheses/patches/f_true.diff. Branch: without --hypotheses, researcher.propose reads the brief + bank + lessons and LLMCoder writes the diff instead.
  4. Workspace.commit_node git-applies the diff in runs/<id>/workspace and copies it to patches/node-001.diff; the runner's run_cfg["candidate_src"] now points at that tree.
  5. Runner.run(node, rung="screen", seed) — _stage_candidate copies template.py + report.py into workspace/node-1/attempt-1/; _build_env drops any inherited variable naming holdout / rulebook / protocols, adds DEVICE SEED WORKSPACE BATCH LR EPOCHS FEATURES and the task's TRAIN VALID; LocalBackend.run Popens the script and polls progress.jsonl.
  6. The candidate trains, calls report.progress and report.checkpoint.save, writes preds.parquet and result.json. Branch: a crash, OOM, hang, or NaN loss is classified by runner.classify and retried once with a halved batch.
  7. synthetic.score(preds, "search") joins by sample_id against the labels the candidate never saw and returns CTR AUC + CVR AUC; measure compares to the incumbent in σ units and returns a verdict; events appends it. Promotion climbs smoke → screen → replicate, and _holdout_if_needed spends one of two holdout visits.
  8. tree._append_lesson writes a row to lessons.jsonl; family_stats re-ranks the queue; app/server.py tails events.jsonl over SSE and reducer.js folds it into the page. Steps 2, 5 and 7 are exactly where the runbook swaps synthetic for KuaiRand.

the rules that hold it together

The candidate sees only what crosses the wall. _build_env is the whole capability model: three task paths plus knobs. Labels never have a path in that dict. Step 4 adds ORACLE and nothing else.
events.jsonl is the only state. Queue order, lessons, the L4 claim, the write-up and the UI are all folds over it; the run header carries the protocol so the log is self-describing.
The spec lives in three hand-synced copies. Protocol yaml declares the output, rules.jsonl demands it, template.py writes it. Change one, change all three, and let the tests catch what you missed.
Who edits ≠ who runs. tree + coder own the diff and the git workspace; runner owns the process. A new search policy touches the first; a new task touches the second and the task adapter.
